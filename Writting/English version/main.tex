\section{Introduction}

Every compilation process essentially consists of three elements. First, lexical, syntactic, and semantic analysis constitute the first point of contact with the source code; the second element is a symbol table, used to organize all the identifiers in the source code; the third is a synthesis phase, in which intermediate code is generated for the final execution of the program.

Under this premise, this work presents the development of the first element of a compiler, specifically the creation of a Lexical Analyzer. Its fundamental objective is to transform a continuous sequence of input characters into a series of syntactically meaningful units called tokens, while discarding non-significant elements such as whitespace and comments.

The result of the project is a Lexical Analyzer capable of producing a token output to validate a character string. In addition, this analyzer considers a list of 45 representative tokens for keywords, identifiers, constants of different types, string literals, operators, and punctuation delimiters.

\subsection{Regular Expressions}
The formal definition of the regular expression for each token class and for each discardable element is presented below.
\begin{align*}
\text{letter} &\rightarrow [\text{a-zA-Z}] \\
\text{digit} &\rightarrow [0\text{-}9] \\
\text{escape} &\rightarrow \backslash\ (\text{any character except newline}) \\
\text{identifier} &\rightarrow (\text{letter} \mid \text{\_})\ (\text{letter} \mid \text{digit} \mid \text{\_})^* \\
\text{keyword} &\rightarrow \text{an identifier lexeme that is in the lookup table} \\
\text{integer} &\rightarrow \text{digit}^+ \\
\text{decimal} &\rightarrow \text{digit}^+\ .\ \text{digit}^+ \\
\text{character} &\rightarrow \text{\textquotesingle}\ (\text{any character except \textquotesingle, } \backslash \text{ and newline} \mid \text{escape})\ \text{\textquotesingle} \\
\text{boolean} &\rightarrow \text{true} \mid \text{false} \quad \text{(recognized as an identifier and looked up in the table)} \\
\text{constant} &\rightarrow \text{integer} \mid \text{decimal} \mid \text{character} \mid \text{boolean} \\
\text{literal} &\rightarrow \text{\textquotedbl}\ (\text{any character except \textquotedbl, } \backslash \text{ and newline} \mid \text{escape})^*\ \text{\textquotedbl} \\
\text{operator} &\rightarrow + \mid - \mid * \mid / \mid \% \mid = \mid == \mid ! \mid != \mid < \mid <= \mid > \mid >= \mid \& \mid \&\& \mid \text{\textbar} \mid \text{\textbar\textbar} \\
\text{punctuation} &\rightarrow ( \mid ) \mid \{ \mid \} \mid [ \mid ] \mid ; \mid , \\
\text{special} &\rightarrow \# \mid . \\
\text{whitespace} &\rightarrow (\text{space} \mid \backslash\text{t} \mid \backslash\text{r} \mid \backslash\text{n})^+ \quad \text{discarded} \\
\text{comment} &\rightarrow // \ (\text{any character except newline})^* \\
&\quad \mid /* \ ([\hat{\ }*] \mid *^+ [\hat{\ }*/])^* \ *^+ / \quad \text{discarded}
\end{align*}
\newpage
For identifiers, the first character may be a letter or an underscore, while the following characters may include letters, digits, or underscores. A decimal requires at least one digit after the point, so ``5.'' is not a complete constant.

The + and - signs are not considered part of numeric constants, but rather independent operators. In this way, an expression such as a-1 is recognized as an identifier, a subtraction operator, and an integer constant.

The ``escape'' token (the \textbackslash{} symbol) applies to strings and character constants; it allows the lexer to add quotation marks or any character other than newline to text strings without it being interpreted as the end of the string. For example, in \texttt{"Hello \textbackslash"John\textbackslash""}, a quotation mark preceded by the escape symbol does not mark the end of the string.

Tokens of type ``Literal'' and ``Character'' do not allow line breaks; consequently, the analyzer reports an error on the line where the string begins if it is not properly closed. Literals refer to strings enclosed in double quotes, "...", while characters are constants that contain exactly one element between single quotes ' '.

Boolean tokens (true and false) are words; they follow the identifier path and are distinguished in the lookup table, so they do not need states of their own. Block comments may contain any content until the closing sequence */ is found. The pattern must prevent an isolated asterisk from closing the comment incorrectly.

The analyzer reads the entire lexeme until it produces a valid token; even if it encounters characters or identifiers associated with a specific token, the lexeme is read completely. Finally, it is compared against the keywords and reserved operators.

These regular expressions serve as the basis for building the automata. In the implementation they will not be used directly through a regular expression library, since they will be represented by the DFA constructed later on.

\subsection{Recognition Priority}
When more than one pattern matches the input, token priority was determined by the following five rules.

\begin{enumerate}
    \item \textbf{Maximal munch.} Take the longest lexeme that ends in a final state.
    \item \textbf{Table before identifier.} If the lexeme ends in $q_1$ and is in the lookup table, the table wins. For example: \cd{int} is a keyword and \cd{true} is a constant.
    \item \textbf{Non-tokens compete equally.} Whitespace and comments are recognized with the same rules and then discarded.
    \item \textbf{Unclosed comment exception.} If the input ends inside a block comment ($q_{10}$ or $q_{11}$), the scanner does not back up to the \cd{/} of $q_8$: an unclosed comment is reported.
    \item \textbf{No final state, no token.} If no prefix reaches a final state, a lexical error is reported; there is no default token.
\end{enumerate}

Maximal munch comes first because it makes the decision in most cases and \textbf{never conflicts with the other rules}. The table comes next because it only acts once the lexeme has already ended in $q_1$. These rules resolve the ambiguity cases considered in the language defined for this assignment.

 Rule four appears in the DFA. If \cd{/* ...} reaches the end without being closed, the last final state visited is $q_8$; without the exception, the scanner would back up and report a \cd{/} operator instead of the actual error.

\section{NFA $\rightarrow$ DFA Conversion}

A DFA has exactly one move per state and symbol, so it runs in a single pass with one table lookup per character. The resulting DFA can be implemented with a transition table, which determines the next state from the current state and the class of the character read.

\subsection{Method, Using the Class Example}

Two operations are used. $\varepsilon$-closure($T$) is the set of states reachable from $T$ using only $\varepsilon$; move($T$, $a$) is the set of states reachable from $T$ on symbol $a$. Each DFA state is a set of NFA states.

\begin{enumerate}
    \item $Q_0 = \varepsilon\text{-closure}(S)$. From $S$, $\varepsilon$ leads to $A$, $D$ and $F$; from $F$, $\varepsilon$ leads to $G$. $Q_0 = \{S, A, D, F, G\}$.
    \item From $Q_0$ on \cd{i}: $A$ goes to $B$ and $D$ goes to $E$. Result $\{B, E\} = Q_1$.
    \item From $Q_0$ on \cd{f}, another letter, or \cd{\_}: only $D$ moves, to $E$. Result $\{E\} = Q_2$.
    \item From $Q_0$ on a digit: $G$ goes to $H$, and via $\varepsilon$ $H$ returns to $G$. Result $\{G, H\} = Q_3$.
    \item From $Q_0$ on \cd{+} or \cd{-}: $F$ goes to $G$. Result $\{G\} = Q_4$.
    \item From $Q_1$ on \cd{f}: $B$ goes to $C$ and $E$ stays in $E$. Result $\{C, E\} = Q_5$.
    \item From $Q_1$ on another letter or a digit: only $E$ moves. Result $\{E\} = Q_2$.
    \item $Q_2$ loops on itself; $Q_3$ and $Q_4$ go to $Q_3$ on a digit; $Q_5$ goes to $Q_2$ on a letter or digit (\cd{ifx} is an identifier).
    \item A DFA state is final if it contains any NFA final state.
\end{enumerate}

Each token class has its own row, so the final state where scanning stops determines the class of the lexeme.

Some operator states behave identically with respect to the input classes, so they can be represented by a single state. For example, the operators \cd{=}, \cd{!}, \cd{<} and \cd{>} share an intermediate state, since they can end on their own or continue with \cd{=} to form a two-character operator. That is why \cd{= ! < >} share $q_{12}$ and all two-character operators end in $q_{13}$. $q_{14}$ and $q_{15}$ are not merged, because $q_{14}$ advances on \cd{\&} and $q_{15}$ on \cd{\textbar}.

Two characters go in the same column if they behave the same in every state. Thus, the 128 ASCII columns are reduced to 18. This grouping avoids defining a separate column for each ASCII character. For example, all letters behave the same way in the transitions associated with identifiers, so they are grouped into class \cd{L}.

The following figure shows a flowchart of the Lexer's scan process.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.85\textwidth]{flujo-escaneo.png}
    \caption{Scanning flowchart}

Each iteration of the loop consumes one lexeme; errors and discarded elements return to the start without adding tokens.

This diagram was derived from the pseudocode: each if becomes a decision diamond, and each group of instructions becomes a box.

\begin{lstlisting}
while pos < len(text):
    state = q0; i = pos; lastFinal = none; lastEnd = pos
    while i < len(text):
        next = delta[state][classOf(text[i])]
        if next == none: break
        state = next; i = i + 1
        if state in FINAL: lastFinal = state; lastEnd = i
    if i == len(text) and state in {q10, q11}:
        errors.report(line, col, "unterminated comment"); break
    if lastFinal == none:
        errors.report(line, col, state); pos = recover(pos, state); continue
    lexeme = text[pos : lastEnd]
    kind = classify(lastFinal, lexeme)   # the lookup table is queried here
    if kind not in {WHITESPACE, COMMENT}:
        tokens.add(kind, lexeme, line, col)
    advanceLineCol(lexeme); pos = lastEnd
\end{lstlisting}

\section{CFG}

The following is the Context-Free Grammar $G_0 = (N, T, P, S)$ for the declaration, with $N = \{\text{Decl}, \text{Type}, \text{Value}\}$, $T = \{\texttt{int}, \texttt{float}, \texttt{char}, \texttt{id}, \texttt{num}, \texttt{=}, \texttt{;}\}$ and $S = \text{Decl}$.

\begin{align*}
&1.\ \text{Decl} \rightarrow \text{Type}\ \texttt{id}\ \texttt{;} \\
&2.\ \text{Decl} \rightarrow \text{Type}\ \texttt{id}\ \texttt{=}\ \text{Value}\ \texttt{;} \\
&3.\ \text{Type} \rightarrow \texttt{int} \mid \texttt{float} \mid \texttt{char} \\
&4.\ \text{Value} \rightarrow \texttt{num} \mid \texttt{id}
\end{align*}

A variable declaration was chosen because it shows a case of productions with a common prefix, which allows left factoring to be applied.

The token sequence \cd{int id = num ;} was taken, and one production was written for each form of the declaration: without a value and with a value. The terminals are tokens from the following catalog:

\begin{center}

There is one consideration for building the LL(1) parser. Productions 1 and 2 share the prefix \cd{Type id}. After reading \cd{int a}, a parser that does not account for this would not know which production to apply; therefore, in an LL(1) table both would fall into the cell $[\text{Decl}, \texttt{int}]$.


%=====================================================================
\section{Left factoring}

The common prefix of $G_0$ was factored out, and the result, $G_1$, was verified to be LL(1). To do so, the longest common prefix of the two Decl productions was identified: $\alpha = \text{Type}\ \texttt{id}$. What follows in each one is $\beta_1 = \texttt{;}$ and $\beta_2 = \texttt{=}\ \text{Value}\ \texttt{;}$. The rule seen in class was applied.

\[A \to \alpha\beta_1 \mid \alpha\beta_2 \quad\Longrightarrow\quad A \to \alpha A', \qquad A' \to \beta_1 \mid \beta_2\]

\begin{align*}
&1.\ \text{Decl} \rightarrow \text{Type}\ \texttt{id}\ \text{Decl}' \\
&2.\ \text{Decl}' \rightarrow \texttt{;} \mid \texttt{=}\ \text{Value}\ \texttt{;} \\
&3.\ \text{Type} \rightarrow \texttt{int} \mid \texttt{float} \mid \texttt{char} \\
&4.\ \text{Value} \rightarrow \texttt{num} \mid \texttt{id}
\end{align*}

The factored grammar is $G_1 = (N', T, P', S)$, with $N' = \{\text{Decl}, \text{Decl}', \text{Type}, \text{Value}\}$, the same terminal set $T$ as $G_0$, the start symbol $S = \text{Decl}$, and $P'$ made up of the productions above. $N'$ includes the new nonterminal $\text{Decl}'$ introduced by the factoring.

The resulting grammar no longer requires left factoring, since the common prefix of the Decl productions has been removed. It was then verified through FIRST, FOLLOW, and the predictive table that it has no conflicts for this example.

\section{Conclusions}
This project delivered a lexical analyzer built from the definition of the grammars all the way to its implementation. A list of 45 tokens grouped into keywords, identifiers, constants, literals, operators, punctuation, and special characters was the first design step; regular expressions were also designed for these tokens. The regular expressions were translated into an NFA of nine sub-automata joined by $\varepsilon$-transitions. This automaton was then converted into a 25-state deterministic automaton using the $\varepsilon$-closure and \textit{move} techniques.

The maximal munch rule, with backtracking to the last final state visited, resolves most ambiguities. Keywords and booleans did not need states of their own, because they are recognized as identifiers and classified with a lookup table. Treating \cd{+} and \cd{-} as independent operators avoids ambiguities in expressions such as \cd{a-1}. The only real nondeterminism in the language, the \cd{/} character, which can either start a comment or be an operator, was resolved in state $q_8$. The unclosed block comment exception prevents the scanner from backing up and reporting a \cd{/} instead of the actual error.

Lexical error handling with panic-mode recovery keeps the analyzer from stopping at the first problem. It reports the line and column and continues with the rest of the input. The staged architecture (reading, preprocessing, scanning, classification, and output), together with a symbol table and an error handler, separates responsibilities and makes it easier to modify each part independently.

Finally, the CFG for variable declarations, with its \textit{left factoring}, FIRST and FOLLOW sets, and LL(1) table, showed how the lexical analyzer feeds the parser. The leaves of the tree for \cd{int a = 10;} are exactly the tokens produced by the lexer, which confirms that both phases are properly connected. As future work, the lexer could be extended with scientific notation, compound operators (\cd{++}, \cd{+=}), or nested comments, and the type of each identifier could be filled in the symbol table during semantic analysis.
